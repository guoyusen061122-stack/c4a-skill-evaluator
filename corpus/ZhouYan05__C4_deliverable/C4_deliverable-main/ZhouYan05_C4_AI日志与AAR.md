## 一、AI 使用日志（过程证据）

### 阶段 1 · 读题与环境勘查

| 我让 AI 做的事 | 结果 | 我的判断 |
| --- | --- | --- |
| 读 C4 挑战正文，提取四条件与交付物清单 | 拿到：可复用/可执行/可验证/IO 明确；5 件交付物 + 命名规则 | 采纳 |
| 勘查课程客户端可用命令 | 发现 `get-challenge` / `check-deliverables` / `prepare-submission` 等 | 采纳 |
| 读两个参考附件（skill-explainer / wechat-doc-mapper） | 确认 `.skill` 包结构：顶层目录=技能名，仅 SKILL.md 必需 | **关键采纳**——直接决定打包方式 |

**教训**：不要凭印象写 `.skill`，先反编译一个真实样例确认结构，省掉整轮返工。

### 阶段 2 · 选题

我让 AI 列候选技能，并**要求必须来自真实踩坑**，不许编。最终选定
`deliverable-selfcheck`，因为它同时满足：可复用（与挑战无关）、可验证
（确定性输出）、零依赖（纯标准库）。

**被 AI 否决的两个方向**：① 又一个"小红书文案助手"——烂大街，不可验证；
② 需要联网调 API 的工具——别人拿到跑不起来，违背"可执行"。

### 阶段 3 · 实现与打包

- AI 写出 `selfcheck.py`（纯标准库）、`SKILL.md`、`references/rulebook.md`、`assets/report_template.md`。
- 打包脚本第一版用了 `tarfile.data_filter` → 在随包 Python 上直接报错。
  改用内联 `norm()` 归一 uid/gid/mode 后通过。
- 验证：`tar -tzvf` 确认 4 个成员、体积和路径都正确。

**教训**：打包环节最容易翻车。写完必须**独立验证**（解包列目录），
不能只看"脚本没报错"。

### 阶段 4 · 自证

写 before / after 两个样本目录，真实跑出 `BLOCKED` → `READY`，
退出码 1 → 0。**工具用自己证明了自检有效**——这是最有说服力的一页。

## 二、AAR 复盘（四个问题）

### 1. 哪些地方做得好？

- **选题对了**：痛点来自自己的真实失败，讲出来别人秒懂，不需要铺垫。
- **验证扎实**：没有停在"能跑"，而是给出了 before/after 对照和退出码。
- **规则沉淀**：把坑写进 `references/rulebook.md` 而不是埋在代码注释里，
  规则变了好维护。

### 2. 哪些地方卡住了？

- **打包**：`data_filter` 兼容性踩坑，浪费了一轮。
- **平台术语**：一开始不清楚通配符到底怎么匹配，试探了几次才确认是
  「字面子串」。→ 已经固化进规则库。

### 3. 如果重做，我会怎么改？

- 先花 5 分钟读一个真实的 `.skill` 样例，再动手写打包脚本。
- 把自检工具的规则做成**可更新的数据文件**，避免以后改规则要动代码。

### 4. 这个技能对别人有什么价值？

它解决的**不是我的问题**——"文件名差一个下划线就被判缺失"是平台级坑，
每个交挑战的人都可能遇到。谁用过之后给我反馈"这次一次过了"，
它就值得迭代 v2。

## 三、传播闭环计划（C4 的核心）

1. **发布**：把 `.skill` 发到 Elite20 群 + 仓库链接。
2. **答疑**：别人跑出问题时，我基于平台真实返回帮他对齐规则。
3. **收反馈**：收集"规则与平台不一致"的案例。
4. **迭代 v2**：更新规则库、加 `--fix` 改名预览、接平台 API 自动拉清单。
