# 阮如意_C4_skill说明：challenge-preflight（挑战交付物提交前预检器）

> **一句话 IO**：**输入**一个挑战交付目录（加挑战编号），**输出**一份提交前自查报告（`PASS` / `FAIL` + 逐条行动项）。

| 项 | 值 |
| --- | --- |
| 技能名 | `challenge-preflight` |
| 可执行交付物 | `阮如意_C4_challenge-preflight.skill`（可安装的技能包） |
| 版本 / 日期 | v1.0 / 2026-10-04 |
| 运行环境 | Python 3.9+，**纯标准库、离线、零第三方依赖** |
| 形态 | Claude Skill 包：`SKILL.md` + `scripts/` + `references/` |

---

## 一、解决什么问题

课程挑战被打回，多数不是内容不行，而是**机械问题**：

| 被打回的原因 | 后果 | 预检如何发现 |
| --- | --- | --- |
| 文件名不符合规范（把 `AI日志.md` 写成 `ai-log.md`） | 平台按文件名匹配必交项，直接判「缺件」 | 用该挑战的必交规则逐条匹配 |
| 少交一个文件（忘了 demo 截图 / 忘了 AAR） | 产物完整性扣分 | 逐条列出「已匹配 / 未匹配」 |
| 正文里还留着未清理的残留标记 | 评审一眼看到，判为未完成 | 全目录关键词扫描 |
| 空文件（建了没写内容） | 等于没交 | 扫 0 字节文件 |
| 把 `.git`、`.scratch`、`node_modules` 一起交上去 | 体积爆炸、泄露临时文件 | 杂物清单 |

**边界很明确**：它只做机械检查，**不判断内容好不好**。内容质量归你和评审，机械问题归它。所以 `PASS` 不等于内容优秀。

---

## 二、使用场景

- 用户说：「提交前预检」「交付物齐了吗」「这个挑战能交了吗」「帮我检查交付目录」
- AI 准备调用平台的 `check-deliverables` / `prepare-submission` / 提交接口**之前** —— **先跑预检，再谈提交**。

---

## 三、输入 / 输出

| | 内容 |
| --- | --- |
| 输入 | `--dir` 交付目录（必填）、`--challenge` 挑战编号 C1–C7（必填）、`--name` 姓名前缀（可选，未给则自动推断） |
| 输出 | Markdown 报告（默认）或 JSON（`--json`）；退出码 `0`=PASS、`1`=FAIL、`2`=参数/环境错误 |

退出码让它能被脚本直接串起来：`python preflight.py … && 提交`。

---

## 四、使用步骤

1. **定位目录**：指向「要上传的那一层」，不要指到里面一层。
2. **运行**：
   ```bash
   python scripts/preflight.py --dir "<交付目录>" --challenge C4 --name 阮如意
   ```
3. **读结论**：第一行就是 `PASS` / `FAIL`。FAIL 只看两件事 —— **缺件**和**空文件**。
4. **修行动项**：报告末尾的「行动项」逐条改。
5. **复查**：改完再跑，直到 `PASS`。同一目录重复运行结果完全一致，可放心反复跑。

## 五、真实案例（可复现）

本次 C4 交付物自查，同一目录、同一条命令跑了两次（2026-10-04）：

- **第 1 次**：`结论：FAIL —— 缺 1 项必交、0 个空文件`，唯一缺件是 **Demo（截图或视频）**。
- **行动**：按行动项补上 `阮如意_C4_demo截图.png`。
- **第 2 次**：`结论：PASS`（退出码 0）。

两次实测输出见交付物 `阮如意_C4_demo截图.png`（左右两版报告拼图）。
这正是它的全部用法：**跑 → 按行动项补 → 再跑**。

## 六、技能四条件自证

| 条件 | 本技能如何满足 |
| --- | --- |
| 可复用（Reusable） | 单文件脚本 + 规则表，离线可跑，不依赖作者环境；换目录/换姓名只改参数 |
| 可执行（Executable） | `python scripts/preflight.py --dir … --challenge C4` 直接运行，无需安装依赖 |
| 可验证（Verifiable） | 有明确退出码（0/1/2）与 `PASS`/`FAIL` 结论；确定性设计，同输入同输出 |
| IO 明确（Clear I/O） | 输入：交付目录 + 挑战编号；输出：`PASS`/`FAIL` + 行动项 |

## 七、规则来源（诚实声明）

规则表在 `references/rules.json`，**每条都带 `source`**：

- **C1 / C2**：来自平台 `prepare-submission` 实测返回的必交清单（真实跑出来的，不是猜的）。
- **C4**：来自 `CHALLENGE.md` 第四节命名表（第 44–50 行）与上传清单（第 292–298 行）。
- **C3 / C5 / C6 / C7**：`"verified": false` —— 未收录。此时脚本只做通用检查，并在报告里明写「该挑战的必交规则未收录，未做齐全性判定」。

> 设计原则：**不知道就说不知道**。宁可少检查一项，也不编一条规则让使用者误判。

支持新挑战：在 `rules.json` 的 `challenges` 下加一项 —— `include` 写正则数组、`min` 写最少命中数、`namePrefixed: true` 表示文件名必须带姓名前缀。
