## 一、用了什么 AI、怎么指挥的

| 项 | 内容 |
|---|---|
| 工具 | WorkBuddy（Agent 模式，可读写文件 + 执行命令） |
| 交互方式 | 不是对话问答，是**给它目标 + 交付标准，让它自己读资料、写代码、跑测试、自我修正** |
| 我的角色 | 定方向、给真实数据、定验收标准、在关键分叉上拍板 |

**我没有一次性说"帮我做个技能"。** 我给的是约束条件：

1. 先读完整资料包（CHALLENGE.md / challenge.json / rubric.json / 样例 .skill）
2. 技能要满足"四条件"，且**必须能用真实数据验证**
3. 零第三方依赖（保证别人拿过去就能跑）
4. 交付到桌面 `C4` 文件夹，结构照 C3 仓库的样子

## 二、时间线（5 轮迭代）

### 轮次 1 — 读资料 + 定方向（14:28–14:33）

**AI 做了什么**
- 读了 `CHALLENGE.md`（330 行）、`challenge.json`、`challenge.yaml`、`rubric.json`
- 读了 `索引_挑战资料清单.csv` —— 这一读就读出了**20 个挑战的完整元数据**
- 解包了两个示例 `.skill` 研究格式

**关键发现（AI 自己发现的，不是我告诉它的）**

`CHALLENGE.md` 第 101 行写：> "打包后的 `.skill` 文件就是一个 tar.gz 压缩包"

**这句话是错的。** AI 实测两个官方样例：
```
head bytes: 504b 0304 → "PK" = ZIP
zipfile.is_zipfile(...) → True
tarfile.open(...)       → ReadError('not a gzip file')
```
→ 我采纳了实测结果，按 **ZIP** 打包。这个判断如果照文档做，交付的包根本装不上。

**为什么选"提交自检器"这个方向**

C4 最高权重是**被使用次数**。我让 AI 按"全组每个人、每个挑战都要重复做哪件事"来选。
答案是：提交。20 个挑战 × 全组人数 = 最高频场景。
对比"论文写作技能""PPT 技能"——那些只有部分人用，而且每个挑战只用一次。

### 轮次 2 — 写代码 + 内置自检（14:33–14:37）

**AI 做了什么**
- 写 `build_registry.py`：从 20 个挑战的 `challenge.json` + `rubric.json` **自动生成** YAML 注册表
  （不手打 = 不会手滑 = 平台更新可一键同步）
- 写 `challenge_submit_guard.py` 主程序
- 为了**零依赖**，内置了一个约 90 行的迷你 YAML 解析器（缩进映射 / 列表 / 列表套字典 / 引号转义）
- 写 `--self-test` 内置自检：5 个合成夹具断言

**第一次打脸（我自己发现的）**

Git Bash 里跑 `tar -tzf "C:/Users/.../xxx.skill"` 报：
```
tar (child): Cannot connect to C: resolve failed
```
Windows Python 不认 Git Bash 的 `/c/` 路径映射。
→ 改用原生 `C:\Users\...` 路径。这个坑后来被我写进了教学说明"常见坑 2"。

**自检结果**：5 / 5 通过。

### 轮次 3 — 真实数据验证，被打脸两次（14:37–14:45）

我要求：**不许用模拟数据交差，必须对桌面上的真实交付包跑。**

#### 打脸 #1：信号匹配把真实内容判成 0 分

对 C3 跑第一版，输出：
```
| 内容实质 | **0.0** | 20 | 20.0 | 0 命中 / 3 缺失 |
```
而 C3 文件夹里有 **34 KB 的真实反思内容**。这明显是误判 ——
rubric 信号词是"提供新信息 / 给出可执行结论 / 有深度视角"，
我的文档里根本不会原样写这几个词，所以精确匹配全部落空。

**修复（v2）**：加三级匹配 —— 原文/同义词命中算 1.0；中文信号退化成 2 字滑窗片段命中算 0.5；找不到算 0。
```
修复后：内容实质 0/20 → 10/20
校准对照：平台实评该维度 17/20
```
单维度校准明显改善（0 → 10，真值 17）。

#### 打脸 #2：粗估 90 分，平台实评 77 分

v2 跑完 C3：
```
交付物 3/3 ✅ ｜ 无红线 ✅ ｜ 粗估 90 / 100
```
而 C3 的平台实评是 **77 分**。差 13 分。

我翻出 C3 的初评说明，根因是：
> "内容实质 17/20、AI 使用 13/15 基本拿满，参与质量 + 协作贡献共约 −15 分，
>  同一根因：评审看到的是『5 篇准备好的稿子』，不是『5 次发生过的参与』。"

**也就是说：文件全齐、零红线，仍然可能丢 13 分 —— 因为"稿子写好了"≠"发出去了"。**
而这件事，脚本读文件读不出来。

**修复（v3）**：加报告第 7 节「机器查不到、必须人工确认的事」：
- 行为是否真的发生（稿子写好了 ≠ 发出去了 —— 直接引用 C3 的 −15 分教训）
- 内容是否真实可复核（宁可留空回填区，不要编）
- 陌生人能否照做
- demo 现在还能不能跑

**这是我的技能里最值钱的一节，而它是被"我的工具给了我一个过于乐观的分数"逼出来的。**

### 轮次 4 — 边界修复 + 打包验证（14:45–15:00）

#### 打脸 #3：小写文件夹名识别失败

对我自己的 `c1`（小写）文件夹跑，直接退出无输出。
原因：识别正则写的是大写 `C\d+`，且当时大小写敏感。
→ **修复（v4）**：`re.IGNORECASE` + 结果统一转大写。

#### 打包与安装验证

- 写 `pack_skill.py` 按 ZIP 打包（结构对齐官方样例：`challenge-submit-guard/SKILL.md` 在最外层）
- **解压到临时目录后重跑 `--self-test` → 5/5 通过**（证明不是"在我机器上能跑"）
- `--strict` 空文件夹 → 退出码 1（门禁可用）

### 轮次 5 — dogfooding：用工具自检自己的提交包（15:45 左右）

**指挥指令**："用它检查它自己所在的 C4 提交包，报告留档。"

#### 打脸 #4：命名检查误报 —— evidence 里留着 C1/C2 的运行记录被点名

对 C4 包自检时，输出：
```
⚠️ 文件名里的挑战号与本挑战不符：evidence/run_C1_real.txt(写作C1)、
   evidence/run_C2_real.txt(写作C2)、evidence/run_C3_real.txt(写作C3)
```
这些是**故意保留的跨挑战运行证据**，不是命名错误。
根因：命名检查对**所有**文件判定"挑战号是否匹配"，但它只该对**必交物**判定。

**修复（v5）**：`check_naming` 只对命中必交物模式的文件判"挑战号不符"，
其余文件只计数不点名。修复后误报清零。

#### 一个有趣的自我引用问题

第一次自检时，工具报"存在空文件：evidence/run_C4_self.txt"——
它自己就是那份报告，`tee` 刚创建、还没写完就被自己扫到了。
**这是扫描时序伪影，不是真问题**（报告写完后重跑即消失）。
已如实留档，没有为了让报告好看而隐藏。

**最终自检结果**（`evidence/run_C4_self.txt`）：
```
交付物 5/5 ✅ ｜ 命名 13 符合 / 11 平铺 ｜ 无红线 ｜ 粗估 100/100（自检 ≠ 官方评分）
```

## 五、AI 用得不好的地方（诚实记录）

1. **第一版信号匹配过于天真** —— 直接拿 rubric 原词做子串匹配，
   在中文长信号上必然大量漏判。应该一开始就设计降级匹配。

2. **粗估公式过于乐观** —— `满分 × 命中率 × (0.6+0.4×完整度)` 在文件齐全时几乎必然给出高分，
   而它完全无法表达"行为没发生"这类真实扣分项。
   我选择**不假装能算准**，而是在报告里明确写"这不是官方评分"并加第 7 节人工确认清单。
   如果重做，我会把粗估改成**区间**而不是单点值。

3. **一开始没做安装后验证** —— 只在源目录跑通了。
   后来补了"解压到临时目录再跑 --self-test"，才敢说别人也能跑。

4. **文档工作量被低估** —— 4 份文档 + demo 比写代码的决策成本高。
