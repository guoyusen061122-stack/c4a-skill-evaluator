# challenge-submit-guard — 挑战提交自检器

## 一句话说明

**输入**一个挑战交付文件夹路径 + 挑战编号，**输出**一份 7 节体检报告：
缺什么、命中哪条红线、最可能在哪丢分、按什么顺序补。

```bash
python challenge_submit_guard.py "C:/Users/me/Desktop/C4"
```

---

## 一、解决什么问题

Elite20 一共 20 个挑战（C1–C10H），每个挑战有 3–5 项**必交交付物**、5–6 个**评分维度**、3 条**红线**。
提交前你脑子里要同时记住十几条规则，而平台 rubric 散落在每个挑战的 `challenge.json` / `rubric.json` 里。

真实会踩的坑，我自己踩过：

| 坑 | 后果 | 什么时候发现 |
|---|---|---|
| 漏交一项必交物 | `artifactCompleteness` 直接压到 ≤5 分 | 评审后 |
| AI日志 只写了两行 | `reflectionQuality` 压到 ≤5 分 | 评审后 |
| 日志里看不出迭代 | `aiUsage` 压到 ≤5 分（判为"一句话指令直接提交"） | 评审后 |
| 文件名没按规范 | 评审和自动化盘点都要靠猜 | 评审后 |
| 交付物是个 0 字节占位文件 | 算没交 | 评审后 |

**共同点：都是提交前 30 秒就能发现、提交后要花一轮返工的问题。**

这个技能把这 30 秒固化成一条命令。

## 四、输入输出

**输入**

- `path`：挑战交付文件夹（必填）
- `-c/--challenge`：挑战编号，如 `C4`；**省略时自动识别**（文件夹名 → 文件名，大小写不敏感）
- 可选：`--json` / `--out 文件` / `--strict` / `--list` / `--self-test`

**输出**（Markdown，7 节）

```
1. 交付物核对   每项必交物的匹配模式 / 状态 / 命中文件
2. 命名规范     符合 vs 不符合「姓名_挑战号_部件.ext」的数量
3. 红线扫描     缺失 / 无AI日志 / 一句话提交 / 空文件（带封顶后果）
4. 五维粗估     每维度信号命中数、缺失信号、封顶标记
5. 提分杠杆     按丢分从大到小排前 3，封顶的标 🔴
6. TODO         按优先级的可执行动作
7. 人工确认     机器查不到的 4 件事
```

---

## 五、使用步骤（3 步，约 1 分钟）

```bash
# 1. 确认环境（看到 5 个绿勾再往下）
python challenge_submit_guard.py --self-test

# 2. 跑体检
python challenge_submit_guard.py "你的/交付/文件夹" -c C4

# 3. 按报告第 6 节 TODO 顺序补 —— 先解红线，再补内容
```

**顺序不能反**：红线会把某维度压到 ≤5 分，此时补内容无效。报告第 5 节会给被封顶的维度标 🔴。

## 六、真实案例（不是模拟数据）

### 案例 1：我自己的 C3 交付包（真实提交、平台已评分）

```bash
python challenge_submit_guard.py "C:/Users/卢怡然/Desktop/C3" -c C3
```

| 项目 | 结果 |
|---|---|
| 扫描 | 7 个文件 / 101.3 KB |
| 交付物 | 3 / 3（AI日志 ✅、AAR ✅、反思 ✅） |
| 红线 | 未命中 |
| 命名 | 0 个符合规范（7 个全部是 `AAR.md` 这种平铺命名） |
| **粗估** | **90 / 100** |
| **平台实评** | **77 / 100** |

**这个 13 分的差距，是本技能最有价值的部分。**

平台扣分说明写的是：「内容实质 17/20、AI 使用 13/15 基本拿满，参与质量 + 协作贡献共约 −15 分，
同一根因：评审看到的是『5 篇准备好的稿子』，不是『5 次发生过的参与』。」

也就是说 —— **文件全齐、零红线、粗估 90 分，真实得分仍然只有 77**，
少的 13 分全部来自「稿子写好了但没发出去」，而这件事**脚本读不出来**。

所以我在报告里加了第 7 节「机器查不到、必须人工确认的事」，第一条就是：
**行为是否真的发生：稿子写好了 ≠ 发出去了。**

### 案例 2：C2 论文交付包

```
12 个文件 / 684.7 KB ｜ 交付物 4/4 ｜ 无红线 ｜ 粗估 77.5 / 100
最大丢分：研究严谨性 -12.5（满分 25）、技术实现 -10（满分 20）
```
指向很清楚：论文包的文件齐全，但**文献严谨性和技术论证这两块在文档里找不到可引用证据**，
是内容深度问题，不是漏交问题。

### 案例 3：C1 翻译管线包

```
104 个文件 / 21.7 MB ｜ 交付物 4/4 ｜ 无红线 ｜ 粗估 100 / 100
```
C1 是自动化管线，脚本/日志/术语表都在，信号命中率高。
**粗估满分不代表稳拿满分**——它只说明「文件夹里能找到证据」，不说明「翻译质量好」。

### 案例 4：空文件夹（负面测试）

```
命中 missing_artifacts + no_ai_log ｜ artifactCompleteness 被封顶到 5 ｜ --strict 退出码 1
```

> 三个案例的原始输出留档在 `evidence/`：`run_C1_real.txt`、`run_C2_real.txt`、`run_C3_real.txt`、`run_c1_real.txt`。

## 七、为什么这么设计

**1. 零依赖 > 功能丰富**

能用标准库解决就不引入 pip 包。「别人拿过去就能跑」比「多一个 Excel 输出」重要得多。
为此我内置了一个约 90 行的迷你 YAML 解析器（缩进映射 / 列表 / 列表套字典 / 引号转义），
没装 PyYAML 也能跑，装了就用 PyYAML。

**2. 规则外置，代码不动**

20 个挑战的交付物模式、评分维度、红线规则全在 `references/challenges.yaml`，
由 `scripts/build_registry.py` **从平台导出的 `challenge.json` + `rubric.json` 自动生成**——
不是我手打的，所以不会手滑。平台更新后重跑一次脚本就能同步，不用改一行代码。

**3. 宁可说「粗估」，不装作「评分」**

分数估计必然不准。但「你在内容实质这一维最可能丢分」这个**指向**是准的，
而且每条都给了证据位置（文件名 + 行号），方便你自己复核。

**4. 内置自检 > 文档承诺**

让别人相信技能能用，最有效的方式是让他自己跑一遍 `--self-test` 看到 5 个绿勾，
而不是读一段「应该可以运行」的说明。

## 八、已知边界（不藏着）

| 边界 | 说明 |
|---|---|
| 分数是粗估 | 对 C3 实测：粗估 90 vs 平台 77。它定位丢分维度，不预测得分 |
| 读不到"行为是否发生" | 稿子齐 ≠ 发出去了。这是 C3 的真实教训，已写进报告第 7 节 |
| 二进制内容不解析 | PDF/DOCX/XLSX 只参与文件计数和交付物匹配，不做内容取证 |
| 片段匹配会偏乐观 | 中文信号退化成 2 字片段匹配（0.5 权重），减少误判 0 分，代价是整体偏乐观 |
| **目前 0 个真实外部用户** | 见 README「传播状态」——不编数字 |
