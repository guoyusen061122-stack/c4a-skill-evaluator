# C4 AAR 复盘（七维）

> 挑战：C4 技能分享与传播
> 日期：2026-09-29
> 复盘者：学生 + AI 协作
> 技能：doc-consistency-auditor（Markdown 文档一致性审计器）

---

## 一、学到了什么

- **"能力产品化"的关键是四条件**：一个技能能否被陌生人直接用，取决于「可复用 / 可执行 / 可验证 / IO 明确」四条件是否同时成立，缺一条就退回成"个人经验分享"。
- **确定性脚本比不可复现的 prompt 更有说服力**：给脚本约定「纯标准库 + 退出码 0/1/2 + 相同输入必然相同输出」，陌生人才能一键复现、才能判断成败——这是"可验证"的落点。
- **让 AI 自证而非自述**：不满足于 AI 说"能检测问题"，而是让它造出带已知 bug 的样例跑出真实报告，用证据闭环代替口头承诺。

## 二、流程（S → A → R）

- **S（情境）**：C4 要求交付一个可安装、可执行、可验证的技能包，附完整使用说明与真实案例。
- **A（行动路径）**：选题评估（四条件）→ 写 SKILL.md（frontmatter+工作流+边界+示例）→ 写确定性脚本 audit.py（R0–R5 规则）→ 写 references 样例（术语表/交付物清单）→ 构造 demo 样例 → 真实自测（干净/坏/目录三态）→ 撰写说明/教学/AI日志/AAR/README → 打包 .skill → 生成 demo 截图 → 推送 GitHub → 平台提交。
- **R（结果）**：技能包结构完整（SKILL.md + scripts + references）、自测三态通过、交付物文档齐备。

## 三、与 AI 协作

- **AI 承担**：四条件选题评估、SKILL.md 与说明文档撰写、audit.py 脚本实现、YAML 样例与 demo 样例构造、报告解读。
- **我承担**：选题定夺、逐轮审阅与真实性核对、复跑自测、授权推送与提交确认。
- **关键协作教训**：AI 初版脚本容易"看起来能跑、实则规则覆盖不全"，必须用带已知问题的样例做回归式验证——干净样例要返回 0，坏样例要精确报出对应 `文件:行号`。

## 四、完成了什么

- 技能四条件评估结论
- SKILL.md（132 行，frontmatter 含 10+ 触发短语）
- `scripts/audit.py`（纯标准库，R0–R5 规则，退出码 0/1/2）

- 交付物文档：skill说明 / 教学说明 / AI日志 / AAR / README

## 五、卡点与突破

- 卡点 1：脚本无法"验证自己是否正确" → 突破：构造带已知 bug 的坏样例 + 干净样例做回归，用退出码和报错位置自证。
- 卡点 2：受控脚本环境禁止用变量/命令替换指定脚本路径 → 突破：改用显式相对路径直接调用 `python3 doc-consistency-auditor/scripts/audit.py`。

## 六、改进方向

- 加一个"自包含冒烟测试"脚本，让安装者一条命令就能复现本说明里的三态自测。
- 术语表 YAML 解析目前只支持极简子集，后续可支持注释内联、多值合并等更复杂写法。
- 补充跨文件锚点、图片资源存在性检查的更细粒度报告。

## 七、ΔR 归因（KSTAR）

- **R̂（预期结果）**：交付一个陌生人可一键复现的 Markdown 一致性审计技能包。
- **R（实际结果）**：技能包结构完整、自测三态通过、文档齐备，符合四条件。
- **ΔR 归因**：
 1. 选题聚焦「确定性脚本」而非「AI prompt」，把"可验证"落到退出码与精确报错上；
 2. 自测阶段用坏样例逼出脚本覆盖问题并修正，而非一次通过；
 3. 交付物命名与清单严格对齐 C4 的「必须提交内容」表，避免漏件。
