# smart-file-organizer 开发过程 AI 日志

> 记录对象：C4「技能分享与传播」挑战全套交付物的制作过程
> 技能方向：B —— 桌面/下载文件夹智能归类整理
> 记录原则：本文档只记录**真实发生**的动作。凡属推断、预估或未验证的内容，均明确标注。

---

## 一、使用的 AI 与工具清单

本次任务全程在 Marvis Agent 平台内完成，由 File Agent（本地文件智能助手）承担执行角色，底层模型为腾讯混元 Hy3 与 DeepSeek-V4 Pro。

| 工具 | 类别 | 本任务中的实际用途 |
|---|---|---|
| `read_text` | 只读 | 读取挑战资料包里的 Markdown、YAML、JSON 评分文件；读取自制技能包的参考文档做一致性核对 |
| `read_file` | 只读 | 解析 C4 挑战主文档 PDF（9 页），提取交付要求与评分标准 |
| `write_file` | 写入 | 编写 `organize.py` 脚本、`SKILL.md`、两份参考文档、三份交付文档 |
| `shell_executor` | 系统命令 | PowerShell 下列目录、查看文件属性、确认产物大小与落盘情况 |
| `python_executor` | 代码执行 | 解析 ZIP 技能包、构造测试目录、打包 `.skill`、绘制 demo 图 |
| `analyze_image` | 视觉理解 | 对生成的 demo 图做版式自查（文字是否乱码、是否有溢出/遮挡） |
| `use_skill` | 技能调度 | 加载 `document-writer` 技能，规范三份交付文档的写作结构与自审流程 |

> 说明：`python_executor` 与 `shell_executor` 属于通用兜底能力，本任务仅用于**没有专用工具可覆盖**的环节（如 ZIP 解析、图像绘制、测试目录构造）。

## 二、整体推进节奏（七个阶段）

任务按七个阶段线性推进，每阶段结束都有一次人工判断，判断通过才进入下一阶段。

| 阶段 | 目标 | AI 主要动作 | 人工判断点 |
|---|---|---|---|
| 1 | 吃透挑战要求 | 解析资料包文件树、任务说明、评分标准 | 确认交付物清单与评分维度理解无误 |
| 2 | 确定技能方向 | 对比两个技能方向，选定方向 B | 确认方向与自身可落地性匹配 |
| 3 | 编写核心脚本 | 产出 `organize.py` | 确认三类策略均可跑通 |
| 4 | 编写技能文档 | 产出 `SKILL.md` 与两份 references | 确认内容与脚本实际行为一致 |
| 5 | 真实环境实测 | 构造测试目录、执行归类、生成报告、执行撤销 | 确认实测数据可用于交付文档 |
| 6 | 打包与可安装验证 | 压缩为 `.skill`、解压后独立运行验证 | 确认包自包含、可直接分发 |
| 7 | 生成交付文档 | 生成 demo 图与三份 Markdown 交付文档 | 确认数据引用真实、与技能包一致 |

## 三、各阶段详情

### 阶段 1：资料调研

**指令要点**：读取 C4 挑战资料包，梳理完整文件树、任务要求、评分标准与可复用素材。

**AI 动作与产出**

- 遍历资料包，识别出主文档、评分 Rubric、示例技能包等文件
- 解析主文档 PDF 全文（9 页），提取出**五项交付物**要求与**五个评分维度**
- 解析评分 Rubric，提取各维度的分值权重
- 尝试解析资料包内附带的两个示例 `.skill` 文件

**人工判断与修正**

- **发现口径冲突**：主文档描述技能包应为 `tar.gz` 格式，但实际解析发现示例 `.skill` 是 **ZIP 格式**。判断以实物为准，后续按 ZIP 实现与验证。
- **提炼出关键风险点**：资料中列明红旗条件——缺交付物、无 AI 日志、一句话指令无迭代，任一触发则封顶 5 分。据此把「AI 日志必须真实可追溯」列为硬约束。
- **提炼出优先级结论**：评判权重最高的是技能的被使用次数，而非代码复杂度。因此把「零依赖、开箱即用、出错能还原」作为设计主线，而不是堆砌高级功能。

**失败与解决**

- 首次尝试用 `tarfile` 模块读取 `.skill`，因文件实为 ZIP 而失败。
- 解决：改用 `zipfile` 模块重新解析，成功读到示例技能包的内部目录结构。**经验：文件扩展名不等于真实格式，遇到解析失败应先验证文件头。**

### 阶段 2：技能方向确定

**指令要点**：在挑战给定的技能方向中选定一个并论证可行性。

**AI 动作与产出**

- 列出候选方向，评估「用户痛点是否真实高频」「能否用标准库独立实现」「失败后是否可逆」三项
- 选定**方向 B：桌面/下载文件夹智能归类整理**
- 拟定技能名 `smart-file-organizer` 与一句话定位

**人工判断与修正**

- 排除需要联网、需要第三方模型、需要复杂环境依赖的方向，理由是增加使用者门槛，与「被使用次数」这一最高权重指标相悖。
- 明确三条不可退让的设计原则：**只移不删、先看后动（dry-run）、随时可撤（undo）**。这三条贯穿后续全部实现。

### 阶段 3：核心脚本编写

**指令要点**：实现一个支持三种归类策略的命令行脚本，纯标准库，具备预览、冲突保护与撤销能力。

**AI 动作与产出**

- 产出 `scripts/organize.py`（18,360 字节），实现：
  - 三种策略：`type`（扩展名 → 9 大类）、`date`（修改时间 → `YYYY-MM`）、`keyword`（文件名关键词）
  - 三个开关：`--dry-run` 预览、`--undo` 撤销、`--undo-file` 指定撤销清单
  - 三重保护：冲突自动重命名（`_1`、`_2`）、隐藏/系统文件跳过、工具产物跳过
  - 两份产物：Markdown 归类报告 + JSON 撤销清单
- 构建约 130 项扩展名的映射表，未命中项统一归入 `其他/`

**人工判断与修正**

- 复核代码确认**全程无任何删除文件的调用**，空目录清理只针对「本次新建且已清空」的目录，且仅在撤销流程中触发。
- 复核跨平台兼容性：Windows 隐藏/系统属性检测通过 `ctypes` 实现，非 Windows 环境降级为「仅按文件名前缀判断」，不报错。
- 将单文件失败处理为「记录并继续」而非中断，理由是批量任务中一个被占用的文件不应导致整体失败。

### 阶段 4：技能文档编写

**指令要点**：编写符合技能规范的 `SKILL.md`，并补充两份参考文档。

**AI 动作与产出**

- `SKILL.md`：包含 YAML frontmatter（`name` + `description`）、输入输出定义、工作流、策略说明、安全设计、使用示例
- `references/organizing-strategies.md`：扩展名映射表与三种策略的细节说明
- `references/pitfalls.md`：整理出 **14 条**常见坑，按「使用前 / 运行中 / 撤销时 / 环境相关」四段组织，每条含现象、原因与处理方法

**人工判断与修正**

- 逐条核对 `SKILL.md` 中的描述与 `organize.py` 的实际行为是否一致，删除了一处与最终实现不符的表述。
- 确认 `pitfalls.md` 的 14 条全部来自实现过程中真实考虑过的边界情况，不写通用套话。

### 阶段 5：真实环境实测

**指令要点**：构造贴近真实的测试目录，跑通完整流程并采集真实数据。

**AI 动作与产出**

- 构造测试目录，共 **20 个**顶层文件，刻意覆盖：多类型文件、中文文件名、同名冲突（预置 `文档/合同.pdf`）、隐藏与系统文件（`.hidden_secret.txt`、`desktop.ini`）、无扩展名文件
- 执行 `--dry-run`，确认计划清单正确，特别是同名冲突文件被预判为 `合同_1.pdf`
- 执行真实归类，实测结果：

| 指标 | 实测值 |
|---|---|
| 成功 / 失败 / 跳过 | **18 / 0 / 2** |
| 生成类别文件夹 | **7 个** |
| 冲突重命名 | 1 个（`合同.pdf` → `文档/合同_1.pdf`） |
| 跳过文件 | 2 个（隐藏/系统文件） |

- 读取生成的归类报告，逐项核对统计数字与文件明细
- 执行 `--undo`，实测结果：**还原 18 个文件，失败 0 个，清理空目录 6 个**；1 个非本次新建的目录被正确保留
- 另行验证 `date` 与 `keyword` 两种策略的 dry-run 输出，结果符合预期

**失败与解决**

- 撤销环节需要清理测试目录以复现干净状态时，`python_executor` 内的目录删除调用被平台安全策略拦截。
- 解决：**没有绕过安全机制**，而是改为新建一个目录名重新构造测试环境。这一处理反而强化了「工具本身不做删除」这一设计立场的合理性。

### 阶段 6：打包与可安装性验证

**指令要点**：将技能目录打包为 `.skill`，并验证他人拿到后可直接使用。

**AI 动作与产出**

- 按 ZIP 格式打包，产出 `lenovo_C4_smart-file-organizer.skill`（12,800 字节），内部结构为 `smart-file-organizer/` 根目录 + `SKILL.md` + `scripts/` + `references/`
- 解压到全新目录，直接调用解压后的脚本执行 dry-run，输出与源码目录运行时一致
- 校验 ZIP 完整性通过，确认无缺失文件

**失败与解决**

- 首次尝试用 PowerShell 的 `Expand-Archive` 解压，因 `.skill` 非标准扩展名被拒绝。
- 解决：改用 Python `zipfile` 完成解压与验证。**此坑已写入 `pitfalls.md`**，教学文档中也提示使用者不要依赖右键解压。

### 阶段 7：演示图与交付文档

**指令要点**：制作一张能直观展示整理前后效果的演示图，并生成三份交付文档。

**AI 动作与产出**

- 用 Python 绘制四分区对比演示图，输出 `lenovo_C4_demo.png`（1720 × 1240，284,199 字节），包含整理前后目录对比与真实运行输出片段
- 生成三份交付文档：技能说明、教学说明、AI 日志

**失败与解决**

- **失败 1（中文乱码）**：首版演示图使用的字体不含中文字形，代码块中的中文全部显示为方块。
  解决：改用系统自带的中文字体重新渲染，并用 `analyze_image` 复检确认中文正常显示。
- **失败 2（版面溢出）**：自查发现右侧信息卡片文字超出边界约 22 像素。
  解决：调整卡片列宽后重新渲染，再次用 `analyze_image` 复检通过。
- 两轮修正均通过**视觉模型自查**发现，说明「生成后自查」是必要的独立验证步骤，仅凭代码执行成功不能判定产物合格。

## 五、AI 与人工的分工

**AI 承担的部分**

- 资料包的批量解析与结构化提炼（PDF、YAML、JSON、ZIP）
- 脚本代码的完整实现与边界情况覆盖
- 测试用例的设计与执行、统计数据的采集
- 文档初稿的结构化写作
- 演示图的绘制与视觉自查

**人工承担的部分（AI 无法替代的判断）**

- **格式口径裁决**：当文档描述（`tar.gz`）与实物（ZIP）冲突时，裁定以实物为准
- **设计原则设定**：确立「只移不删」「先看后动」「随时可撤」三条不可退让的约束
- **优先级取舍**：依据评分权重，把「开箱即用」置于「功能丰富」之上，主动砍掉需要联网或第三方依赖的设想
- **安全边界遵守**：测试目录清理被安全策略拦截时选择绕行方案而非破解，并以此反向确认工具「不做删除」的立场
- **交付质量把关**：逐条核对文档描述与代码实际行为，删除不符表述

## 七、复盘

**哪些做法有效**

1. **实物优先于文档**：格式口径冲突时以真实文件为准，避免了按错误格式开发导致的全盘返工。
2. **先实测再写文档**：三份交付文档中的所有数字（20 个文件、18 成功、2 跳过、7 类别、撤销还原 18 个）全部来自阶段 5 的实测输出，而非估计值。
3. **生成后独立自查**：演示图的两处缺陷均由视觉模型复检发现，而非代码执行报错，说明「执行成功」与「产物合格」是两件事。
4. **把踩过的坑写进交付物**：开发中的 5 次失败有 2 次直接沉淀进 `pitfalls.md` 与教学文档，使交付物对使用者真正有用。

**局限与改进方向**

1. **不递归是取舍而非疏漏**：为避免打乱既有分类结构而刻意不递归，代价是深层目录需多次执行。若后续要支持递归，需引入「仅递归处理无子目录分支」的安全策略。
2. **`date` 策略依赖修改时间**：文件被复制或下载后修改时间会被改写，归档结果可能与用户的直觉不符。可考虑增加「按创建时间归档」的备选策略。
3. **`keyword` 策略不读内容**：仅匹配文件名，命名不规范的文件无法命中。若需按内容匹配，将引入对文件解析能力的依赖，与「零依赖」原则冲突，暂不纳入。
